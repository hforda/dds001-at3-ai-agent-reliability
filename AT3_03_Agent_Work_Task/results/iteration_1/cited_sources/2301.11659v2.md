[s0] Dedicated tensor accelerators demonstrate the importance of linear algebra in modern applications.

[s1] Such accelerators have the potential for impressive performance gains, but require programmers to rewrite code using vendor APIs — a barrier to wider scale adoption.

[s2] Recent work overcomes this by matching and replacing patterns within code, but such approaches are fragile and fail to cope with the diversity of real-world codes.

[s3] We develop ATC, a compiler that uses program synthesis to map regions of code to specific APIs.

[s4] The mapping space that ATC explores is combinatorially large, requiring the development of program classification, dynamic analysis, variable constraint generation and lexical distance matching techniques to make it tractable.

[s5] We apply ATC to real-world tensor and linear algebra codes and evaluate them against four state-of-the-art approaches.

[s6] We accelerate between 2.6x and 7x more programs, leading to over an order of magnitude performance improvement.

[s10] 2024 ========================================================================================================================================================================================================================================================================================================================================================================================================================================================================================================================================================================================================== § INTRODUCTION Linear algebra is a fundamental building block of many of today's critical applications;

[s11] from weather modeling <cit.> to ubiquitous DNN <cit.> workloads.

[s12] Its importance is reflected in the large number of accelerator libraries and hardware devices devoted to fast linear algebra.

[s13] These range from specialized devices such as Google's TPU <cit.> to the tensor cores on NVIDIA <cit.> among many others <cit.>.

[s14] While such devices promise significant performance for an important class of applications <cit.>, their uptake is limited by their programmability <cit.>.

[s15] Typically, these accelerators and libraries are accessed via calls to specialized APIs, meaning existing code has to be rewritten.

[s16] Given the volume <cit.> and variety <cit.> of existing legacy code, such rewriting is a significant undertaking <cit.>.

[s17] The combined importance of linear algebra acceleration and the difficulty of rewriting legacy code to accelerators has led to recent work which attempts to automate the process.

[s18] These techniques search user code for matrix multiplications using constraints <cit.> or polyhedral analyses <cit.> and replace regions of code with appropriate API calls or instructions.

[s19] However, as we show in Section <ref>, these approaches are fragile.

[s20] Constraints capture only a limited set of program patterns and small variations in the user code defeat them.

[s21] While they work well on curated benchmarks, they perform poorly on real-world code <cit.>, defeated by function calls, optimized code and inline assembler.

[s22] Neural classification (e.g.

[s23] <cit.>) can effectively detect code despite these challenges.

[s24] However, it does not provide a path to acceleration, but requires further steps.

[s25] These include generating variable mappings and checking for equivalence  <cit.> which has shown promising results for Fourier Transforms.

[s26] However, one of the key challenges in matching code to APIs is the cost of searching for user program variables that map to API formal parameters.

[s27] As the width of the API and complexity of the user program increase, this becomes combinatorially expensive.

[s28] As we show in Section <ref> existing approaches <cit.> fail to scale to the challenges that linear algebra APIs present.

[s29] We present ATC, a compiler that applies program synthesis to compile general user-code to linear algebra accelerators.

[s30] We identify and solve key challenges enabling the detect/synthesize paradigm to scale to the more complex APIs of linear algebra acceleration.

[s31] In addition, ATC employs a trained platform predictor to determine whether acceleration is profitable or not.

[s32] We applied our approach to 50 GitHub GEMM and 15 convolution projects and discovered between 2.6 and 7x more linear operators compared to KernelFaRer <cit.>, IDL <cit.>, Polly <cit.> or FACC<cit.>.

[s33] This resulted in more than an order of magnitude performance improvement.

[s34] This paper makes the following contributions: * We present ATC, which maps matrix multiplication and convolution programs to hardware accelerators, up to 7x more frequently than existing techniques.

[s35] * We introduce novel heuristics to reduce the mapping search space by four orders of magnitude.

[s36] * We develop novel dynamic analyses to determine higher-level information about variables, enabling synthesis without costly whole-program analyses.

[s37] § MOTIVATION §.§ Exisiting Match and replace IDL and KernelFaRer Both aim to detect linear algebra operations in user programs and replace them with an appropriate accelerator library call.

[s38] To illustrate this consider the code in Figure <ref>.

[s39] This shows a straight-forward matrix multiplication program fragment, from the parboil benchmark suite <cit.>.

[s40] They aim to detect this matrix-multiplication and replace it with a call to the library, shown at the bottom of the diagram.

[s41] To replace code with an API call they have to both detect the code performing a matrix multiplication and also determine which user program variables correspond to the arguments of the API call.

[s42] Both approaches are able to detect that this is a matrix multiplication, and can determine the mapping between user variables and API parameters.

[s43] §.§ Examples of complex GEMM programs Unfortunately, in practice, user code can be complex such that code structure or pattern-based approaches inevitably fail.

[s44] As an example, consider the code found on GitHub shown in Figure <ref> which implements a matrix-multiplication algorithm (only a fragment of the 120 lines of user code are shown here).

[s45] The code structure is complex and difficult to understand as it makes extensive use of inline assembler intrinsics which defeats the code structure analysis approaches of IDL and KernelFaRer, preventing acceleration.

[s46] §.§ Our approach - ATC Rather than relying on code structure to guide detection, ATC uses behavioral equivalence to determine if a section of code is a linear algebra operation.

[s47] Firstly, ATC uses neural program classification <cit.> to detect that the code in Figure <ref> is probably a GEMM.

[s48] It then searches variable matches to determine the potential source and output arrays.

[s49] As the search space is combinatorially large, we introduce scalable, algorithm-independent heuristics (which we discuss in Section <ref>) that keep the number of mappings manageable.

[s50] Next, ATC generates different input values for the arrays and records the output.

[s51] After generating many randomized inputs, it observes that it has the equivalent behavior to the corresponding API and is able to replace the AVX2 code with the GEMM call at the bottom of Figure <ref>.

[s52] Legality Now, IO behavioral equivalence is not proof that a section of code is a particular linear algebra operation - similarly IDL and KernelFaRer do not prove equivalence.

[s53] For proof, bounded model checking based on Kleene <cit.> can be deployed.

[s54] In practice, as demonstrated in our experimental section, IO equivalence gives no false positives.

[s55] For further guarantees, we can ask for programmer sign-off or employ model checking.

[s56] Profitable Once we have detected and can replace a section of code with an accelerator call, we need to determine if it is profitable to do.

[s57] Due to hardware evolution, we do not use a hard-wired heuristic to determine profitability.

[s58] Instead, we learn, off-line, a simple predictive model to determine if the target accelerator is faster than a CPU implementation.

[s59] The model is called at runtime, determining if offloading is worthwhile.

[s60] FACC Behavioral equivalence is also employed in FACC <cit.>.

[s61] Unfortunately, it is restricted to FFTs and one-dimensional arrays, and cannot detect the replacement in Figure <ref>.

[s62] Therefore, we extended FACC to FACC* to consider GEMMs and multi-dimensional arrays.

[s63] This, however, exposes its weak variable binding model which is combinatorial in the number of user array variables and their dimensionality.

[s64] Furthermore, it relies on program synthesis to determine the length of arrays, which scales poorly to problems with many potential length parameters for arrays such as GEMM.

[s65] FACC also relies on brittle inter-procedural liveness analyses to determine the liveness status of variables.

[s66] This restricts it to running only at link time, rendering it invalid for use in shared libraries.

[s67] We will see in Section <ref> that the combination of these issues results in excessively large search spaces.

[s68] § SYSTEM OVERVIEW Figure <ref> gives a system flow overview of ATC.

[s69] We first detect regions of code that are likely to be linear algebraic operations using a neural program classifier.

[s70] The classifier is trained ahead of time, based on programs that are equivalent to the accelerator and prior examples of linear algebra code.

[s71] Once candidate code sections have been identified, we apply program analysis to match user program variables with the particular API formal parameters.

[s72] Given the combinatorially large search space, we develop novel techniques to make the problem tractable.

[s73] For each candidate matching, we generate multiple data inputs, execute the user code section and record the output values.

[s74] If the input/output pairs correspond to the input/output behavior of the accelerator API, we can say they are behavioral equivalent and candidates for replacement.

[s75] While candidate user code may be replaceable with a call to an accelerator API, it may not be profitable.

[s76] Therefore, we employ a simple ML classifier, trained offline, and invoked at runtime to see if acceleration is appropriate for the user code for the runtime known array sizes.

[s77] §.§ Neural Program Classification To detect potentially acceleratable parts of a program, we use prior work in neural program classification <cit.>.

[s78] A network is trained with multiple instances of different program classes.

[s79] We use the OJClone dataset <cit.>, which includes 105 classes of different programs, and add examples of the programs that we want to detect e.g.

[s80] GEMMs and convolutions, gathered from benchmark suite repositories other than GitHub.

[s81] At compile time a new candidate program is divided into functions, which are presented to the neural classifier.

[s82] The classifier assigns each function in the program a probability of belonging to a certain class.

[s83] We consider the most probable class, which in the case of a GEMM or convolution is then considered for variable matching and eventual code replacement as described in the following sections.

[s84] Classification is fast (≤ 1.5 sec) and has negligible impact on compilation time (see Section <ref>).

[s85] § VARIABLE MATCHING To check if a section of user code is behaviorally equivalent to the API, we have to match up the user program variables with API formal parameters.

[s86] We first detect what variables are livein/liveout (Section <ref>) and then the dimensions of arrays (Section <ref>).

[s87] §.§ Detecting livein and liveout variables Detecting livein and liveout variables via standard static analysis is straightforward for well-structured programs but fails for more diverse real-world codes, which may use assembly code or intrinsic functions.

[s88] ATC uses dynamic analysis to determine which variables are livein and liveouts inside a function.

[s89] In C, variables are passed by value so non-pointers variables are always livein.

[s90] In the case of pointers (or arrays), we generate random inputs with arbitrary sizes.

[s91] If the values in memory change after executing the program, the array is considered liveout.

[s92] This allows us to detect which variables are livein or liveout, but not both livein and liveout at the same time.

[s93] We generate a new random input for liveout variables and re-execute the function.

[s94] If the output differs from the first execution, it is both livein and liveout.

[s95] We implement this algorithm as a just-in-time compiler pass in LLVM <cit.>.

[s96] §.§ Detecting the dimensions of arrays Detecting arrays length enables offloading of appropriately-sized regions of codes, so it is a critical step in ATC.

[s97] For some programs, lengths can be found using static analysis (e.g.

[s98] <cit.>), but this fails in more complex cases.

[s99] We use runtime analysis to determine which program variables define array size using a modified form of runtime array bound checking.

[s100] For each set of variables that could define an array's size (typically, from the argument list), we set such variables to a fixed value.

[s101] We then execute the user code that is modified to check runtime array accesses.

[s102] First, the compiler selects a target array to find its size.

[s103] Then, to generate the modified program, we tweak the load and store instructions in the user program, replacing them with custom function calls in the IR.

[s104] If a load or store does not access the array we are interested in, we modify it to load and store at a constant, safe location.

[s105] If it does, the instruction is replaced with a function call that will check at runtime if the access is out of bounds.

[s106] If so, the program exits with a custom error code.

[s107] If not, we have found a valid array size.

[s108] The basic idea is depicted in Figure <ref>.

[s109] This is used by our JIT analysis as shown in Algorithm <ref> and implemented in LLVM.

[s110] This way, the compiler can assign different input sizes to a given array and check the exit code.

[s111] Therefore, the compiler iterates over all the possible dimensions combinations until one of the executions does not end with the custom error exit code.

[s112] That means that the program was completed without any illegal access to the target array, which indicates that it is the right dimension of the array.

[s113] § REDUCING THE MATCHINGS SEARCH SPACE To match code to APIs, the compiler generates different candidates for the variable to formal parameter mappings and then tests them using IO equivalence.

[s114] For small APIs, all mappings can be explored, but the combinatorial cost makes it prohibitive for real-world accelerator APIs.

[s115] We develop techniques that reduce the mapping space by exploiting arrays information and human coding styles.

[s116] §.§ Exploiting array information Using array dimensions (Section <ref>), we can reduce the number of possible matches that must be checked, as assigning one array to another means that the dimensions of each array must line up.

[s117] §.§.§ Automatic matching algorithm We first generate all n!

[s118] permutations of the n array variables to n parameters mapping.

[s119] We discard all permutations where variable livenesses do not match.

[s120] Then for each candidate user array and parameter array pair, we generate the constraints defining how their dimensions match.

[s121] If we find contradictory constraints for any permutation, we discard it.

[s122] The algorithm is shown in Algorithm <ref>.

[s123] §.§.§ Automatic Matching Algorithm: Example To illustrate this, Figure <ref> shows an example where we have two functions with three 2D arrays each.

[s124] First, the algorithm generates all the permutations between 0 and n-1 (n=3 in this example).

[s125] Then, for each permutation, it tries matching each variable in every array in the user code with the corresponding variable in the array of the API (here we show only three of the six possible permutations).

[s126] In the first case (with the permutation [0, 1, 2]), the algorithm tries matching the array variables of the user program X, Y, Z with API parameters A, B, C .

[s127] We then examine each of the variables defining each of the corresponding arrays.

[s128] Comparing X and A gives a match of x0 → y0 and x1 → y1.

[s129] For the second array variable Y and API parameter B, we have x1 → y1 and x2 → y2 and for the third variable pair Z,C we have x2 → y2 and x0 → y0.

[s130] All of these are consistent with n=3 constraint, which satisfies the condition ( in Algorithm <ref>).

[s131] Liveout information is also satisfied so this permutation is added as a potential mapping.

[s132] In the second permutation [1,0,2], where X,Y,Z maps to B,A,C, the constraints are inconsistent e.g.

[s133] x1→ y2 and x1 → y0 leading to 6 ≥ 3, so it is not a valid match.

[s134] In the third and last example, constraints are equal to n, but the liveout arrays do not match.

[s135] Thus, the only valid match is the one found in the first permutation.

[s136] §.§ Using argument names Programs are developed by humans, so we can assume that the functions that humans write follow common patterns.

[s137] We exploit this by analyzing the argument names of the API and the user program to find lexical similarities.

[s138] To compare argument names, we use the Levenshtein distance <cit.> to compute the distance between each of the user programs and API arguments.

[s139] Figure <ref> shows the definition of the Levenshtein distance, which calculation is based on the minimal number of modifications needed to transform one word into another, representing how close are those words.

[s140] After computing the distance, the compiler selects the combination that minimizes the Levenshtein distance.

[s141] Figure <ref> shows an application example of the Levenshtein distance to a real case of GEMM matching.

[s142] For calculating the distance, we strip the API suffix () and convert all names to lowercase.

[s143] Results show that the most probable mapping for is in the user code, and for is , which are the right matches.

[s144] §.§ IO generation Once we have a candidate match we generate random inputs of different sizes and test for input-output (IO) equivalence.

[s145] We use 30 inputs of varying sizes.

[s146] Although IO behavioral equivalence is not proof, we can increase the number of tests for increased confidence.

[s147] No existing technique such as IDL or KernelFaReR can prove that a matched piece of code is provably equivalent to an API and therefore rely on user sign-off.

[s148] §.§.§ Behavioral Equivalence and the Limits of Verification ATC, like prior work on floating-point accelerators <cit.>, uses behavioral equivalence.

[s149] The downside of this strategy is that it requires programmer sign-off to make any substitution.

[s150] However, due to the complexities of verifying floating-point programs <cit.>, verification of such liftings are some way off.

[s151] In summary, the key challenges that all competing techniques face are: * Floating-point numbers often raise challenges in theorem provers as they are challenging to reason about.

[s152] * Floating-point functions may have different accuracies in different input ranges, meaning that the obvious checks of correctness (even within bounds) are difficult to apply.

[s153] The backend of ATC is not tied to using behavioral equivalence.

[s154] As we will see, the use of such behavioral equivalence results in no false positives.

[s155] Further development of theorem prover technologies would mean that the weak behavioral equivalence in ATC could easily be replaced with a theorem prover guaranteeing correctness and enabling automatic transformations.

[s156] § AUTOMATIC PROFITABILITY DETECTION We assume that user code runs faster when replaced by a platform-specific library.

[s157] The question is whether it is best to run on a CPU or accelerator version (XPU) of the library.

[s158] This in turn depends on the input size, which is only known at runtime.

[s159] We use a predictive model based on empirical data to enable accurate predictions as platforms and libraries evolve by retraining the model.

[s160] SVM We use the well-known support vector machine (SVM) classifier with a polynomial kernel of degree 3 with gamma=1 and C=100.

[s161] We sample the CPU and the accelerator with a common dataset of input sizes, which produces a dataset that is small enough to be processed in less than five minutes, but large enough to be highly accurate.

[s162] Data is labeled with 0 or 1 meaning that the CPU or the XPU is faster.

[s163] The model is then trained and deployed at runtime, when matrix sizes are known, The training phase is done only once, at “factory time”, and the resulting model when deployed has negligible (≤ 0.3 msec) runtime overhead (see Section <ref>).

[s183] §.§ Methods We evaluate our approach against 4 well known schemes: IDL: Idioms are described using an idiom description language <cit.>, which is translated into a set of constraints over LLVM IR.

[s184] KernelFaRer: Uses different pattern matching to detect specific code constructs, matching specific matrix-multiplication structures <cit.>.

[s185] Polly: Detects static control parts (SCoPs) in the code using the polyhedral model <cit.>.

[s186] It does not replace the code with a call to an optimized library.

[s187] FACC*: FACC uses neural embeddings and behavioral synthesis to detect candidates for acceleration <cit.>.

[s188] It is limited to 1D arrays so we developed an extended version, FACC*, which supports multi-dimensional arrays.

[s200] 11 out of 50 cases.

[s201] FACC* Unlike the other approaches, FACC* performed poorly on naive implementations, but better on others.

[s225] §.§ Candidate search complexity and compile time One of the key challenges in matching code to APIs is searching for program variables that map to API formal parameters.

[s226] As the width of the API and complexity of the user program increase, this becomes combinatorially expensive.

[s227] Figure <ref> evaluates FACC* naive matching of variables and our approach based on the Levenshtein distance.

[s228] Naive matching varies considerably from just 4 candidates to over 1 million.

[s229] Our approach greatly reduces the number of candidates for the majority of the programs.

[s230] There is one special case, code 23, where we reduce the number of candidates, but it is still too high.

[s231] Figure <ref> shows the compilation time of ATC.

[s232] The initial neural classifier has a negligible constant execution time of 1.3 seconds, while the other phases' compilation time grows with the number of candidates.

[s233] As the number of candidates begins to increase compilation time becomes prohibitively expensive.

[s234] Code 23 has 280 candidates which would take 35 mins more to evaluate.

[s235] We limit the number of candidates considered to 100 which corresponds to a timeout of ≤ 10 minutes.

[s247] § RELATED WORK Matching in Programs Matching high-level program structure has been used to discover parallelism <cit.>, heterogenous offloading <cit.> and many other core compiler tasks <cit.>.

[s248] Constraint languages make these tasks easier <cit.> but their constraints are very sensitive to code structure <cit.>.

[s249] For matrix multiplications in particular, KernelFaRer <cit.> provides a more robust approach, detecting characteristics that define matrix multiplications.

[s250] Polyhedral analyses can also be used to target matrix multiplication accelerators <cit.>, but both these techniques fail to scale to the diversity of real code.

[s251] FACC <cit.> uses IO equivalence, which is robust to program structure, but only addresses the challenges of FFTs and does not scale to longer function signatures used for GEMM.

[s252] To support any accelerator type, the compiler should support multi-dimensional arrays, while FACC only supports 1D arrays.

[s253] Because in 1D arrays and FFTs the search space in matching the API parameters is small, FACC does not include anything to reduce it.

[s254] With more complex programs and domains, this limitation makes compiling programs intractable.

[s255] Mask <cit.> uses symbolic execution to prove equivalence, which does not work well for floating-point problems.

[s256] Fuzzy classification techniques based on code clone detection <cit.>, domain-classification <cit.>, pattern matching <cit.>, code embeddings <cit.> and identifiers <cit.> can be used to help compile to accelerators <cit.>.

[s257] These classification strategies are able to classify diverse code structures, but do not provide a compilation strategy for using an accelerator on their own.

[s258] A large class of techniques focus on migrating between APIs.

[s259] These techniques often use program synthesis <cit.>, NLP <cit.> and code embeddings <cit.>.

[s260] These techniques are unable to extract existing code into APIs.  ← **本簡報引用此句**

[s261] Compiling for GEMM Accelerators Existing compilation strategies largely focus on lowering code from intrinsics to accelerators using rewrite rules <cit.> and synthesis techniques <cit.>.

[s262] Existing approaches to extracting matrix multiplications <cit.> are brittle.

[s263] Synthesis-based techniques <cit.> and rewriting-based techniques <cit.> have been developed to extract these DSLs that can then be lowered: but they largely require flexible DSLs, rather than APIs presented by hardware accelerators.

[s264] Performance Prediction Predicting code the performance of hardware accelerators is challenging, as the break-even point may depend on many different arguments within a function's interface <cit.>.

[s265] LogCA <cit.> introduces static performance comparison models for hardware accelerators and similar models have been applied in offloading tasks <cit.>.

[s266] Machine learning has often been applied in profitability settings, such as OpenCL Kernels <cit.> and OpenMP <cit.>.

[s267] Similar techniques have been applied to FPGAs, by estimating power/performance <cit.> and tracking actual performance <cit.>.

[s268] § CONCLUSIONS This work presented ATC, a flexible domain-agnostic compiler that matches legacy linear algebra code to accelerators.

[s269] By using IO behavioral equivalence and smart search space reduction, we are able to match over 80% of challenging real-world programs to accelerator APIs, significantly outperforming all alternative approaches.

[s270] Supporting new domains different from GEMM and convolution is easy because ATC focuses on behavior rather than code structure, which makes it very flexible and extensible.

[s271] Furthermore, to support other accelerators in GEMM or convolution, only the accelerator API is needed: ATC adapts to the new specification automatically.

[s272] Future work will examine how to further reduce the search space using online learning and to expand the complexity of user code considered.

[s273] Longer-term, we wish to automatically target a range of accelerators with diverse functionality, matching and transforming user code to maximize performance.
